# v0.5.0 Burst Ergonomics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make large payloads a one-sentence story — "set `MaxPayload`; big
things are handled for you" — by (a) chunking oversize stream messages inside
shared memory so streams no longer force resident cap-sized slab classes, and
(b) adding an intent-level `PluginSpec.MaxPayload` field from which geometry,
burst ceiling, and chunk ceiling are all derived, so no adopter ever again
hand-computes a burst ceiling or a per-direction slab ladder.

**Architecture:** Stream chunking is an additive shared-memory protocol
feature: a new reserved frame kind (`STREAM_CHUNK = 9`) behind a negotiated
feature flag, authorized by the frozen ABI's additive rules (`shm-abi.md`
§19). The sender splits a logical stream message larger than the direction's
inline limit into ladder-sized fragments that ride the same ring in order;
the receiver reassembles them under the stream's per-frame sequence
discipline. Chunking introduces a second unit of accounting — fragment
sequence numbers versus logical-message credits — so the frozen stream
contract is amended (additively, behind the feature) wherever it currently
equates the two. With chunking in place, the `MaxPayload` derivation needs no
knowledge of which methods stream in which direction — the stock ladder
serves every direction, burst carries oversize unary, chunking carries
oversize stream messages, and one number bounds both.

**Tech Stack:** Go 1.26, protobuf via buf codegen (`internal/control`),
existing shm transport (`internal/transport/shm`), rpcruntime stream layer
(`internal/rpcruntime`), testify, chaos/differential harnesses under
`tests/`, `make ci` validation.

## Verdict on the device-gateway feedback

The feedback from the device gateway's burst adoption (the first burst
adopter) proposes three changes: a `BurstAuto` ceiling sentinel, an
intent-level `MaxPayload` field with shape-aware per-direction geometry
derivation, and in-shm chunking of oversize stream frames. Code archaeology
against v0.4.0 confirms the diagnosis but reorders the remedies:

1. **Chunking first, and it is the headline.** The frozen ABI's own
   extension rules make it possible: §19 permits assigning a reserved frame
   kind (§5's 9..255 range) behind a negotiated feature with no
   `layout_version` bump, and Appendix A's chunking sketch endorses
   RPC-layer chunking as a direction (its Path 2 text contemplates chunking
   over the already-frozen stream kinds; this plan instead assigns a new
   reserved kind, which §19 independently authorizes — Appendix A supports
   the direction, §19 authorizes this encoding). The stream protocol's
   ordering guarantees (`stream-protocol.md` §3.1/§3.3: per-direction FIFO,
   exact-sequence delivery, lossless) make receiver reassembly a
   contiguous-append loop, not a resequencing problem. The gateway's ingress
   path (external payload → plugin→host stream send) is structurally
   unreachable by burst — `internal/rpcruntime/burst.go:967-970` routes only
   unary kinds, and the receive side poisons the connection on any stream
   frame arriving over the socket (`burst_receive.go:520-544`) — so chunking
   is the only fix for that direction, on its own merits.

2. **The shape-aware `MaxPayload` derivation is unimplementable as proposed —
   and unnecessary once chunking lands.** The feedback assumed styx knows
   per-direction stream shapes at spawn. It does not: `ServiceRequirement` is
   `{Service, MinVersion, MaxVersion}` only (`host.go:295`), the handshake
   carries service name+version pairs with no method shapes
   (`internal/control/control.proto:41-44,71`), and the shape table exists
   only plugin-side (`stream.go:688-708`). Deriving asymmetric geometry from
   shapes would require extending the handshake wire contract — surface whose
   entire purpose evaporates once chunking removes the "streams must fit a
   slab" rule. With chunking, `MaxPayload` derivation is shape-blind: stock
   ladder both directions, burst ceiling and chunk ceiling both set from the
   one number. This plan implements that simpler derivation.

3. **`BurstAuto` should not ship.** Three strikes, each verified:
   - The natural sentinel encoding collides with a legal input:
     `math.MaxUint32` is an accepted, test-pinned literal ceiling
     (`host_test.go` accepts `BurstMaxPayload: math.MaxUint32` and pins its
     wire round-trip), so `^uint32(0)` cannot change meaning; a companion
     bool field would become API residue the moment `MaxPayload` lands.
   - Its resolved value is a silent no-op for symmetric geometry: with the
     stock ladder in both directions, "just above the tallest class" yields a
     ceiling whose usable band above the shm inline limit is under ~130
     bytes — burst configured, burst dead, `Start` happy. That is the
     explainability failure inverted. The gateway's own helper returns 0
     (burst off) in that case rather than a resolved value, which is the
     tell: "auto" has no good answer without knowing the intended payload
     bound — which is exactly what `MaxPayload` states.
   - `MaxPayload` deletes the ceiling arithmetic for every adopter who can
     use the derived path. The retained cost is stated honestly: an adopter
     who must keep a hand-built geometry (memory-constrained, custom
     ladders) still computes an explicit burst ceiling under the strict
     inequality — the expert path keeps v0.4.0 semantics unchanged by
     design, and that residual arithmetic is the price of not adding a
     second auto mechanism to the expert path.

4. **Routing oversize stream frames over the burst socket stays rejected.**
   The receive path treats any stream frame on the socket as a
   connection-poisoning protocol violation precisely to protect stream
   ordering; chunking preserves ordering for free by staying on the ring.
   Revisit only with measured ring-occupancy evidence from a real workload.

The feedback's non-goals are honored as stated: no per-direction ceilings, no
independent burst on/off flag, no slab-count knob for any derived class.

## Decisions

All nine were ratified by Arlo on 2026-08-07, after external review
converged (three rounds, final verdict ready-to-implement) and a
decision-by-decision walkthrough. Ratification notes beyond the text
below: the attach-time refusal ships without rollout-ordering guidance
(pre-1.0, the typed error's remedy text is the documentation), and
set-aside throttling is accepted as the designed behavior for chunked
trains that outrun the arena (credits stay an independent per-stream
option).

- **D-1 — Drop the `BurstAuto` sentinel entirely.** v0.5.0 ships
  `MaxPayload` instead; no v0.4.x patch release. Rationale in verdict item
  3, including the honestly-stated residual: expert-path adopters with
  custom geometry keep computing an explicit ceiling.
- **D-2 — Chunking covers STREAM_MSG frames only.** The single
  server-streaming request riding STREAM_OPEN and the single
  client-streaming response riding STREAM_CLOSE remain bounded by the
  sending direction's inline shm limit (~1 MiB on the stock ladder), failing
  loudly with `ErrPayloadTooLarge` when exceeded. The named production
  workload (ingress dispatch over a server-streaming message channel) is
  MSG-path; OPEN/CLOSE chunking stays additive headroom for later (the
  reserved-kind mechanism extends to those kinds behind a future feature).
  This exception is named in `MaxPayload`'s godoc (D-6).
- **D-3 — Chunking activates only through the derived `MaxPayload` path.**
  The expert path (hand-set `Geometry`/`BurstMaxPayload`) keeps v0.4.0
  semantics exactly — no new expert knob, honoring the adopter feedback's
  own non-goals. Internal config carries the chunk ceiling so tests can
  drive chunking directly.
- **D-4 — The chunk marker is a new reserved frame kind, and chunking
  introduces two explicit units of accounting.** `STREAM_CHUNK = 9` (from
  `shm-abi.md` §5's reserved 9..255 range) marks every fragment except the
  last; the final fragment rides an ordinary `STREAM_MSG`, completing the
  logical message. **Fragment sequence numbers** — the existing per-direction
  control-word counter — are consumed by *every* fragment, `STREAM_CHUNK`
  and `STREAM_MSG` alike, and checked per frame by the receiver.
  **Logical-message counts** govern credits, `STREAM_ACK` control values,
  and delivery — one unit per logical message regardless of fragment count.
  `STREAM_CLOSE`'s final-sequence word (`F`) counts fragment sequences (the
  last sequence number the sender consumed), matching the receiver's
  existing `F == expectedSeq−1` acceptance check unchanged. The frozen
  stream contract currently uses one counter for both roles because today
  every logical message is exactly one frame; Task 1 amends it — additively,
  gated on the feature — everywhere it binds sequence, credit, ACK, or
  close accounting to `STREAM_MSG`. Kind choice rationale: `FrameKind`
  already flows end-to-end through `transport.Frame`, the writer, the
  descriptor, and dispatch — a flag bit would additionally require a new
  `Frame.Flags` field plumbed through both transports plus `allowed_flags`
  mask surgery, for identical semantics. An old receiver seeing kind 9
  without the feature poisons the region fail-closed per §5.
- **D-5 — One credit per logical message; the send side runs an explicit
  train state machine; fragments ride train-owned memory.**
  - The sender admits once (one credit) per `SendMsg` before the first
    fragment. The train is **invisible** until the first fragment's enqueue
    is attempted; it is **visible** from that attempt onward unless the
    attempt returns a proven never-published rejection.
  - While invisible: a proven never-published failure — exactly the
    `transport.NeverPublished` set, which is `ErrUnimplementedFrameKind`,
    `ErrPayloadTooLarge`, and reject-mode `ErrBackpressure`
    (`internal/transport/transport.go:193-216`; `ErrClosed` is NOT in the
    set and never proves non-publication) — rolls back the credit and the
    reserved sequence via the existing rollback rule — v0.4.0 behavior,
    whole-train. Any non-proven first-fragment failure makes the train
    visible and falls to the classes below.
  - Every visible-train failure belongs to exactly one normative class,
    each with a defined local outcome and a defined, already-legal
    peer-visible result:
    1. **Reject-mode `ErrBackpressure` on fragment k** (proven never
       enqueued): retry fragment k — same fragment, same reserved
       sequence — under an rpcruntime-owned backoff with named constants
       (the shm writer's internal set-aside constants are not an API),
       whose interval is capped and whose sole exhaustion condition is
       the send context ending. There is no separate attempt or elapsed
       bound: this mirrors block-mode admission, which also blocks until
       the context ends, so "backoff exhaustion" is not a distinct
       failure class — it resolves to class 2.
    2. **Send context ends mid-train** (before or after an enqueue — the
       data lane can return a context error after enqueue, with the
       writer still free to publish the abandoned intent later): the
       existing post-admission context terminal applies unchanged — local
       outcome CANCELED or DEADLINE via the existing terminal mapping,
       peer-visible teardown exactly as today's post-admission send
       context error emits it (the local-cancellation teardown pair the
       receiver already accepts). The lifecycle-lane teardown may
       overtake published fragments; the receiver's terminal-discard rule
       (Task 1) clears the pending accumulation, and any later-arriving
       fragments of the dead train are ordinary late frames disposed per
       the frozen §4.5 rule.
    3. **`ErrClosed` or transport poison** (any fragment, any
       visibility): the connection itself is failing; the stream's
       terminal fans out through the existing connection-teardown path,
       and the terminal-discard rule clears partial accumulations on
       both sides. No new peer frame exists or is needed. Poison keeps
       its existing connection-fatal escalation unchanged.
    4. **Any other transport error**: treated as class 2's
       local-cancellation shape — one terminal transition recording a
       definitive local outcome that wraps the underlying cause
       (surfaced from `SendMsg` and every subsequent call), with the
       same legal peer-visible teardown pair.
    In every class the credit is deliberately not released (the stream is
    dead; its window dies with it — per-stream counters, so no other
    stream's window is affected), the final `STREAM_MSG` is never sent,
    and the whole-message rollback helper is never invoked after
    visibility.
  - Because an abandoned data-lane intent may still publish after a
    context-error return (`internal/transport/shm/writer.go` submit: the
    writer may emit the abandoned intent; acceptance is final), fragments
    must never alias memory the caller can reuse: the chunker copies the
    oversize payload once into a train-owned buffer before the first
    enqueue, slices fragments from it, and keeps it reachable until every
    fragment's fate is reported or the stream terminates. The one extra
    copy of a large payload is measured by the bench task.
- **D-6 — `MaxPayload` is a capacity guarantee, not an enforced cap.** It
  means: "styx will carry any marshaled frame handed to it up to this many
  bytes, on the covered surfaces" — unary request/response bodies (shm or
  burst) and logical STREAM_MSG messages (shm or chunking). It is not a new
  rejection bound: values at or below what the transport already carries
  add no enforcement, and oversize sends beyond the derived ceilings fail
  with the existing definitive `ErrPayloadTooLarge`. Adopters add their own
  envelope before choosing the value. The two exceptions are named in the
  field's godoc: STREAM_OPEN/STREAM_CLOSE payloads (D-2), and the
  transport interlock (D-8).
- **D-7 — `MaxPayload` never shrinks geometry.** A value at or below the
  certain-fit bound of the stock ladder derives the stock geometry with
  burst and chunking both off — the guarantee is already met, nothing is
  enabled, nothing new is rejected. Memory-constrained deployments keep
  using the expert path (`GeometryLean`, custom ladders).
- **D-8 — The `MaxPayload` guarantee is validated against the transport
  that will actually carry it, and refused loudly when unmeetable.** The
  ordinary uds transport has a fixed frame cap this plan does not change
  (`internal/transport/uds.go` default max frame, 1 MiB) and no burst or
  chunking. Therefore: `TransportUDS` pinned with `MaxPayload` above that
  cap is a `*ConfigError` at `Start`, before spawn. At attach — after
  negotiation, when the checksum choice and therefore the connection's
  **exact** per-direction inline maxima are known — the interlock
  compares `MaxPayload` against those exact limits, not against the
  derivation's pre-spawn worst-case bound: burst/chunking support is
  required only when a covered surface's actual inline maximum is
  smaller than `MaxPayload` (so a checksum-off stock attach carries
  payloads up to the full top class inline, and an old feature-mute peer
  in that band is accepted, not refused). When the requirement is real
  and unmet — `TransportAuto` negotiated down to uds with `MaxPayload`
  above the uds cap, or an shm peer that left burst or chunking
  unresolved with `MaxPayload` above the exact inline limit — the attach
  fails with a typed `*IncompatibleError` naming `MaxPayload` and the
  missing capability, at startup, never as a surprise on the first large
  send. The operator's remedies are stated in the error: upgrade the
  plugin or lower `MaxPayload`.
- **D-9 — `StrictCapacity` semantics are unchanged by the derived path.**
  The derived stock profile's top class has 8 slabs; `StrictCapacity` with
  a `MaxDataInflight` above a reachable class's usable slab count keeps
  failing attach with the existing typed STRICT error. The validation
  matrix pins the combination and the configuration guide documents the
  pairing (a strict derived profile needs `MaxDataInflight` sized to the
  smallest reachable class), but no new validation is added at `Start` —
  the existing attach-time check is the single source of that refusal.

Two late decisions, ratified 2026-08-08 after the matrix's discoveries:

- **D-10 — Retire the streaming startup load gate.** The frozen
  `stream-protocol.md` §4.2 requirement to validate
  `(S1) N_max·S_max ≤ max_data_inflight/2` at startup and refuse to load
  is amended away: no code ever enforced it, the remedy configuration it
  prescribes was never built, and enforcing it now would break the
  documented lean profile. (S1) remains as provisioning guidance — the
  same standing the half-window property already has under chunking. A
  host-local validation rule, not wire behavior; peer interop is
  untouched.
- **D-11 — The three pre-existing public error-contract defects are
  fixed in this release**, not deferred: the terminal-error publication
  window in which `Err()` reports nil; the bare internal closed-transport
  sentinel escaping through blocked sends (and the raw
  already-closed-direction string escaping a second `CloseSend`); and a
  post-deadline send reporting the canceled sentinel instead of the
  recorded outcome. The matrix's documented workarounds become the
  regression assertions (each carries a tighten-when-fixed note naming
  its site).

## Global Constraints

- **Frozen contracts:** `docs/specs/shm-abi.md` and
  `docs/specs/stream-protocol.md` section numbers are a stable interface.
  Changes are additive and feature-gated, consuming reserved space per
  `shm-abi.md` §19 and `stream-protocol.md` §11. No `layout_version` bump;
  no renumbering. Where existing normative sentences equate frame sequence
  with logical-message count, Task 1 amends them with explicitly
  feature-conditional text ("when `stream-chunking` is resolved …") rather
  than rewriting their unconditional meaning for old peers.
- **SPSC invariant:** exactly one writer goroutine owns each direction's
  ring and arena. The chunker submits fragments through the existing
  `Transport.Send` admission; it must not add a second producer or reorder
  the data lane's FIFO (`stream-protocol.md` §3.1: set-aside carries park
  without letting later data past).
- **One sender per direction per stream** (`stream-protocol.md` §3.1):
  concurrent `SendMsg` on one stream is already a programming error; the
  chunker relies on this for fragment contiguity and must document that
  reliance where it splits.
- **Fail closed:** an unassigned frame kind poisons the region
  (`shm-abi.md` §5); nothing in this plan may soften that. Kind 9 becomes
  assigned *only* on a connection where the feature resolved true and the
  ceiling is non-zero; everywhere else — dormant shm attaches, every uds
  connection — it stays unimplemented/poisoning, pinned by tests.
- **Backpressure is typed, never silent** (`shm-abi.md` §18): arena
  exhaustion parks the head fragment as a set-aside carry
  (`internal/transport/shm/writer.go:774-784` backoff), surfaced via
  `styx.arena.setaside.count`. Chunking rides this unchanged.
- **Layering** (`.agents/rules/100-project-map.md`): the root `styx` package
  is the only public import; chunk mechanics live in `internal/rpcruntime`
  and `internal/transport`; the only public surface added by this plan is
  `PluginSpec.MaxPayload` and its documentation.
- **Benchmark-first for hot paths** (`.agents/rules/800`): the chunk path
  adds per-fragment work and one train-owned copy to oversize stream sends;
  Task 8 records before/after stream throughput and allocs, and proves the
  sub-inline fast path did not regress. The existing gated cells must not
  regress (alloc gate is median-of-three windows).
- **Overflow-safe arithmetic:** every size comparison involving
  `chunk_max_payload`, accumulated lengths, or `credits × ceiling` products
  is performed in `uint64` (or subtraction form) — never by adding
  `uint32` lengths before comparing. `math.MaxUint32` is a legal ceiling
  and must not wrap any bound.
- **Branches, commits, validation:** per `.agents/rules/600` and `500` —
  Conventional Commits, bodies hard-wrapped at 72 characters, `make build
  vet lint test` (or `make ci`) before any merge; `gh` for PRs.
- **Naming:** all committed text says "the device gateway", never the
  consumer project's name; no plan/review jargon in commits, comments, or
  docs.

### Task 1: Spec amendment — the chunking contract and two-unit accounting

Amend the frozen stream contract before any code. Chunking splits what is
today one counter into two roles; every normative sentence that relies on
their identity must gain feature-conditional text. Disagreements found while
drafting come back to the plan, not into improvised code.

**Files:**
- Modify: `docs/specs/stream-protocol.md` — a new top-level chunking
  section following the streaming feature's template, **plus**
  feature-conditional amendments to every section that binds sequence,
  credit, ACK, or close accounting to `STREAM_MSG`: at minimum the
  kind/control-word table (§2), sequencing (§3.1-3.3), credits and rollback
  (§4.4-4.5), close accounting (§6.4), ACK validation, and the feature
  registry (§11). Each amendment is a "when `stream-chunking` is resolved"
  clause; unconditional v1 text keeps its exact meaning for peers without
  the feature.
- Modify: `docs/specs/shm-abi.md` (record the kind-9 assignment in the §5
  frame-kind table's assigned list, marked feature-gated; one-line pointer
  from Appendix A's chunking sketch to the new stream-protocol section —
  phrased as §19 authorizing this encoding, since Appendix A's own sketch
  contemplates the frozen kinds)
- Modify: `docs/specs/stream-conformance-vectors.md` (new vector group)

(The design doc has no feature registry — no feature, including burst, was
ever listed there; names live in `internal/control/handshake.go` and the
feature docs in `docs/configuration.md`. Nothing to register. The design
doc's stale "chunking/bulk transfer is roadmap" sentence is updated by
Task 7's sweep instead.)

**Interfaces:**
- Consumes: `shm-abi.md` §5 (reserved kinds 9..255), §19 (additive rules);
  `stream-protocol.md` §3.1/§3.3 (sequence + lossless ordering), §4.4-4.5
  (credits, rollback), §6.4 (close), §11 (feature machinery).
- Produces: the normative text later tasks cite — feature name
  `"stream-chunking"`, kind `STREAM_CHUNK = 9`, `AttachRegion` field 7
  `chunk_max_payload`, the two accounting units, the violation list, the
  termination rules, and the conformance vectors.

- [ ] **Step 1: Write the chunking section.** Normative content, stated in
  the spec's voice:
  - **Feature:** name `stream-chunking`; boolean flag, no parameters
    (§11.1); offered optional by both sides; active iff the negotiated
    transport is shared memory ∧ the flag resolved true ∧ the attach carried
    a non-zero `chunk_max_payload`. Mirrors the burst feature's activation
    conjunction exactly. On every connection where it is not active —
    dormant shm attaches and all uds connections — kind 9 remains
    unassigned: an shm receiver poisons on it (§5), and the uds transport
    never implements it regardless of the `streaming` flag.
  - **Wire form:** a logical stream message whose marshaled length exceeds
    the sending direction's inline payload limit is emitted as N fragments:
    fragments 1..N−1 ride frame kind `STREAM_CHUNK` (9), fragment N rides
    `STREAM_MSG` (4). Every fragment carries the stream's call ID,
    service/method words, the logical message's budget word, and its own
    **fragment sequence number** in the control word — the per-direction
    counter every `STREAM_CHUNK` and `STREAM_MSG` frame consumes. Fragment
    payload lengths: every fragment except the last is exactly the sending
    direction's inline limit; the last is the remainder (1..limit bytes). A
    `STREAM_CHUNK` frame never carries an empty payload.
  - **Two accounting units, stated explicitly:** fragment sequence numbers
    order frames within a direction and are checked per frame
    (`expected_seq` semantics unchanged, now spanning both kinds).
    Logical-message counts govern the credit window (§4.4: `sent` and
    `consumed` count logical messages; a chunked logical message consumes
    exactly one credit unit; its `STREAM_CHUNK` fragments consume none),
    `STREAM_ACK` control values (cumulative *logical messages* consumed),
    and delivery. `STREAM_CLOSE.F` counts **fragment sequences**: it is the
    last sequence number the sender consumed in that direction, so the
    receiver's `F == expected_seq − 1` check is unchanged. A worked
    example is normative: first logical message in two fragments, then
    close — `CHUNK(seq=1)`, `MSG(seq=2)`, `ACK(control=1)`,
    `CLOSE(F=2)`; after a second single-fragment message,
    `ACK(control=2)` is legal while the final fragment sequence is 3.
  - **Sequence reservation:** a fragment's sequence number is reserved
    before its `Send` and retained after any possibly-accepted `Send`.
    Rollback of a reservation is legal only while the train is invisible
    (no fragment's enqueue attempted, or the sole attempt returned a proven
    never-published rejection) — the §4.5 rollback rule restated for
    trains. A visible train's failure follows the termination rules below.
  - **Reassembly:** the receiver appends `STREAM_CHUNK` payloads to a
    per-stream accumulation in sequence order; the next `STREAM_MSG`
    completes the logical message, delivered once, whole, consuming one
    credit unit. Accumulation bounds are checked in arithmetic that cannot
    wrap (the ceiling is a full-range `uint32`).
  - **Bounds:** `chunk_max_payload` bounds the reassembled logical message
    on both sides — send-side before the first fragment leaves (definitive
    `PAYLOAD_TOO_LARGE`, pre-visibility, rollback-eligible), receive-side
    as accumulation proceeds. One value governs both directions, announced
    host→plugin on the attach message; the plugin adopts it verbatim (the
    burst ceiling's announce-not-negotiate pattern).
  - **Violations** (each a conformance violation poisoning per §3.3): a
    fragment sequence gap; accumulation exceeding `chunk_max_payload`
    (checked before buffering the breaching fragment); a `STREAM_CHUNK`
    whose payload length differs from the direction's inline limit (the
    canonical form makes every non-final fragment exactly that length —
    short and empty chunks alike are violations, closing the
    descriptor-amplification hole where one credit could otherwise drive
    one descriptor per payload byte); a final `STREAM_MSG` completing a
    pending train with an empty payload (the remainder is 1..limit; an
    empty `STREAM_MSG` stays legal only when no train is pending);
    **a `STREAM_CHUNK` arriving after its direction's `STREAM_CLOSE`**
    (the dual of the frozen contract's existing post-close `STREAM_MSG`
    violation — checked against the close bit before any sequence
    mutation or append); **a `STREAM_CLOSE` arriving in a direction
    whose accumulation is non-empty** (a half-close cannot legitimately
    interrupt its own direction's train — the check runs before any close
    state is mutated); kind 9 without the feature (already §5's
    unassigned-kind poison — restate, don't re-legislate).
  - **Termination:** silent discard of a partial accumulation is reserved
    for genuinely terminal events — `STREAM_ERR`, teardown `CANCEL`,
    connection failure, local terminal transition — where the stream's
    terminal status already reports the failure; the logical message was
    never delivered. The sender-side dual is D-5's normative failure
    taxonomy, restated in the spec's voice: a visible train's context
    expiry produces the existing local-cancellation teardown pair (whose
